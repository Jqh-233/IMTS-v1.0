# IMTS AI 引擎优化 — 需求分析

## 背景

当前 `ai/` 目录存在四个问题：

1. **调度顺序不合理**：混合模式下每封邮件都先调 LLM，但约 80% 的邮件仅靠规则就能判定。规则能秒杀的邮件也花了 API 钱和等待时间。
2. **AI 判断过程对用户不可见**：邮件被跳过时不告知原因，低置信度任务不展示判断依据，用户只能盲信系统。
3. **规则引擎输出无意义的置信度**：规则是二值判断——要么命中要么没命中，不存在"75% 确定"。当前硬编码的 `confidence: 0.0` 是占位符。
4. **拒绝策略过严**："系统通知"、"登录提醒"这类弱非任务词也会导致邮件被跳过，但"系统通知：请于6月5日前完成安全培训"明明是任务。

## 需求一：规则先行分层调度

**现状**：混合模式下，每封邮件 → LLM → 失败才用规则兜底。

**改为**：邮件 → 规则引擎先筛，三层分流。

| 分类 | 条件 | 处理方式 |
|------|------|------|
| 明确是任务 | 行动词 + 时间词 + 请求词三者全中 | 规则提取基础字段（priority、category），LLM 作为"监督者"只润色 task_name 和 deadline |
| 明确不是任务 | 强非任务词命中（验证码、广告、促销、自动回复、Steam 交易等） | 直接跳过，不调 LLM |
| 拿不准 | 有行动词但无时间、有请求词但无行动词等一切边界情况 | 交给 LLM "指挥官"全权判断，LLM 失败时规则兜底创建任务（宁可误报） |

**为什么不会退化**：规则能判定的本来就能判定，拿不准的照样调 LLM。本质上是把顺序调对了。

**LLM 角色拆分为二**：

- **监督者**（规则已确定是任务时）：只确认规则判断 + 润色 task_name/deadline，输出 2-3 个字段，小模型也能胜任。简单的任务名（如"提交周报"）不需要润色，只对模糊主题（如"请看一下"）才提炼。
- **指挥官**（规则拿不准时）：全权判断，输出全部字段。约束放宽——宁可误报，不可漏报。

## 需求二：AI 透明度

只在两个场景展示判断理由：

1. **被跳过的邮件**：在邮件抽屉中展示具体跳过原因。规则模式展示命中词（如"命中广告过滤词'促销'"），LLM 模式展示模型的 reason 字段。
2. **低置信度任务**（confidence < 0.7）：任务卡片上展示 LLM 的判断依据。

高置信度任务不需要解释——有价值的信息才值得占用屏幕空间。

## 需求三：规则模式不输出置信度

规则引擎是二值判断——要么命中要么没命中，不存在"75% 确定"。当前 `confidence: 0.0` 硬编码是无意义的占位符。

- 规则命中 → 前端不显示置信度标签
- LLM 补充/判断 → 前端显示 LLM 的置信度
- 实现方式：前端判断 `confidence_source !== 'rules'` 时才展示

## 需求四：宁可误报，不可漏报

两个错误的代价不对称：

- 多一张误生成的任务卡片 → 用户花 2 秒删掉
- 漏一个真任务 → 用户可能错过考试、漏掉客户、耽误审批

**改为**：仅强非任务词触发跳过。弱非任务词（系统通知/登录提醒/账单已生成）不再拦截，交给后续判断。

核心理念：只有**显然不是任务**的才拒绝。存疑的，一律倾向于创建任务。

## 需求五：任务卡片增加发件人

发件人是邮件自带的现成字段，不需要额外提取逻辑。看板上一眼判断邮件来源（"老板发的还是系统发的"），快速筛查。

展示方式：任务卡片分类下方，一行灰色小字。

> 地点暂不独立提取——格式过于多样（A213、302会议室、腾讯会议），LLM 润色 task_name 时附带进去即可，如"参加习概论考试（A213，6/6 10:45）"。

# 首次实施复盘（2026-05-31）

## 实施概要

基于上述五条需求，对 `ai/` 目录及前后端进行了全面重构。涉及 15 个文件、351 行新增、119 行删除。最终因多个严重缺陷导致系统不可用，回退至初始提交。

## 实施方法

1. 将 `should_create_task()` 替换为三分法 `classify_email()`（确定任务/确定非任务/不确定）
2. 重写 `extract_task()` 调度逻辑：规则先行 → LLM 监督者润色（definite_task）/ LLM 指挥官判断（uncertain）
3. 升级 `prompt_engine.py`：指挥官 prompt（放宽约束）+ 监督者 prompt（只润色 3 字段）
4. 新增 `polish_with_llm_supervisor()`：合并规则结果与 LLM 润色
5. 放宽 `task_schema.py` 校验：过期日期不拒绝、低置信度改为标记不拒绝
6. 数据库新增 `skip_reason`、`decision_reason` 字段，通过 `_ensure_column()` 迁移
7. 前端 TaskCard 加置信度条件过滤、发件人显示、低置信度理由展示
8. 前端 EmailDrawer 展示跳过原因
9. 额外穿插：接入硅基流动 API、Qwen 关思考逻辑

## 出现的问题（按时间序）

### 问题 1：硅基流动超时

**表现**：配置硅基流动 Qwen3-8B 后同步报 Network Error。

**原因**：在 `_call_llm()` 中加了 `"siliconflow" in config["api_base"]` 条件，触发了 DeepSeek 专有的 `thinking: {type: "disabled"}` 参数。硅基流动 API 不认识此参数，处理异常导致超时。

**教训**：跨平台 API 参数不能按域名直接复用。不同服务商的参数集合不同，应按具体服务商文档做适配。

### 问题 2：definite_task 路径静默丢邮件

**表现**：纯 LLM 模式下，明确的任务邮件被跳过。

**原因**：`definite_task` 路径调 `polish_with_llm_supervisor()` 失败时，代码写的是 `if mode == "llm": raise`，异常抛到同步循环的 `except Exception: pass` 被吞掉，邮件标记为已处理但没生成任务。

**教训**：监督者是一个辅助角色，它失败时不应抛异常，应回退到规则结果。核心判断的可靠性不应依赖 LLM。

### 问题 3：数据库迁移不执行（根本原因）

**表现**：前端邮件列表、任务列表全部空，后端无显式报错传达给前端。

**实验验证**（事后复原场景）：

```
1. 创建临时数据库，emails 表不含 skip_reason 列
2. 用重构后带 skip_reason 声明的 SQLAlchemy 模型查询
3. SQLite 报错：
   OperationalError: no such column: emails.skip_reason
   
   生成的 SQL：
   SELECT emails.id, ..., emails.skip_reason FROM emails
```

**确认**：SQLAlchemy 会将模型声明的所有列写入 SELECT 语句。数据库缺少任一列即抛 OperationalError，返回 500，前端看到空列表。

**根本原因**：`init_db()` 函数内含 `_ensure_column` 迁移逻辑，但该函数在 `main.py` 中从未被调用。SQLAlchemy 模型声明了字段、数据库没有 → 查询炸。

**为什么同步本身没受影响**：`save_email()` 使用 raw sqlite3 的 INSERT 语句，不经过 SQLAlchemy ORM。INSERT 不依赖 `skip_reason` 列（列有默认值或允许 NULL），所以邮件能正常存入。同步能干活，读列表不能。

**教训**：任何新增数据库字段，必须先确认迁移代码在应用启动时被实际调用。改 ORM 模型的同时必须确保对应 DDL 已执行。

### 问题 4："同步 0 封"假象（问题 3 的连锁反应）

**表现**：用户两次点击同步，第一次列表仍空，第二次显示"同步完成：0 封邮件，提取 0 个任务"。

**原因链**（经实验验证）：

```
第 1 次同步：
  IMAP 正常抓取 → raw sqlite3 INSERT（不依赖 skip_reason）→ 邮件存入 ✓
  → 任务提取正常 → 返回"10封邮件，N个任务" ✓
  → 前端调 GET /api/emails 刷新列表
  → SQLAlchemy: SELECT ... skip_reason ... FROM emails
  → SQLite: no such column → 500 ✗
  → 前端列表空 → 用户误以为没同步成功

第 2 次同步：
  IMAP 抓取 → message_id 已存在 → 去重 → new_ids = []
  → 返回"0封邮件，0个任务" ✗
  → 用户确认"系统坏了"
```

**唯一根因是问题 3**。问题 4 是它的连锁反应。同步本身一直正常工作，读列表的接口炸了，加上前端错误消息没透传，造成了"同步 0 封"的假象。

## 错误模式总结

四个问题中，问题 3（数据库迁移不执行）是**唯一根因**。其他三个问题：

- 问题 1（硅基流动超时）：独立的 API 兼容问题，与核心重构交叉导致排查困难
- 问题 2（definite_task 静默丢邮件）：独立的逻辑缺陷，`except: pass` 掩盖了它
- 问题 4（同步 0 封）：问题 3 的连锁反应，不是独立问题

共同的教训：

1. **数据库字段变更必须作为第一步**：模型声明新字段 → DDL 必须立即执行 → 验证列存在。这个顺序不能乱。模型和 DDL 分离（ORM 声明 vs raw SQL 迁移）是根源——两边不同步时没有编译期检查。
2. **改动范围过大**：核心重构期间穿插硅基流动接入，问题交叉增加了排查难度。
3. **静默失败**：`except Exception: pass` 吞掉了所有错误信息。无论是数据库查询失败还是 LLM 调用失败，用户都看不到任何提示。

## 改进建议

1. **数据库字段变更作为第一步，验证后再改逻辑**：ORM 模型加字段 → `init_db()` 确认被调用 → 重启 → 查 PRAGMA 确认列存在 → 然后再写依赖新字段的业务逻辑。模型和 DDL 不同步没有编译器检查，只能靠流程保证。
2. **每步独立验证，不等最后**：改一个模块立即重启服务跑一遍确认，不攒 15 个文件一起验证。
3. **核心重构期不改外围功能**：硅基流动接入应在重构稳定后进行。
4. **消灭静默失败**：`except Exception: pass` 替换为错误记录，至少让前端能展示"X 封邮件提取失败：原因"。
