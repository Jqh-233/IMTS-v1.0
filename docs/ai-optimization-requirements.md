# IMTS AI 引擎优化 — 需求分析

## 背景

当前 `ai/` 目录存在四个问题：

1. **调度顺序不合理**：混合模式下每封邮件都先调 LLM，但约 80% 的邮件仅靠规则就能判定。规则能秒杀的邮件也花了 API 钱和等待时间。
2. **AI 判断过程对用户不可见**：邮件被跳过时不告知原因，低置信度任务不展示判断依据，用户只能盲信系统。
3. **规则引擎输出无意义的置信度**：规则是二值判断——要么命中要么没命中，不存在"75% 确定"。当前硬编码的 `confidence: 0.0` 是占位符。
4. **拒绝策略过严**："系统通知"、"登录提醒"这类弱非任务词也会导致邮件被跳过，但"系统通知：请于6月5日前完成安全培训"明明是任务。

## 需求一：规则先行分层调度

**现状**：混合模式下，每封邮件 → LLM → 失败才用规则兜底。

**改为**：邮件 → 规则引擎先筛，三层分流。

| 分类 | 条件 | 处理方式 |
|------|------|------|
| 明确是任务 | 行动词 + 时间词 + 请求词三者全中 | 规则提取基础字段（priority、category），LLM 作为"监督者"只润色 task_name 和 deadline |
| 明确不是任务 | 强非任务词命中（验证码、广告、促销、自动回复、Steam 交易等） | 直接跳过，不调 LLM |
| 拿不准 | 有行动词但无时间、有请求词但无行动词等一切边界情况 | 交给 LLM "指挥官"全权判断，LLM 失败时规则兜底创建任务（宁可误报） |

**为什么不会退化**：规则能判定的本来就能判定，拿不准的照样调 LLM。本质上是把顺序调对了。

**LLM 角色拆分为二**：

- **监督者**（规则已确定是任务时）：只确认规则判断 + 润色 task_name/deadline，输出 2-3 个字段，小模型也能胜任。简单的任务名（如"提交周报"）不需要润色，只对模糊主题（如"请看一下"）才提炼。
- **指挥官**（规则拿不准时）：全权判断，输出全部字段。约束放宽——宁可误报，不可漏报。

## 需求二：AI 透明度

只在两个场景展示判断理由：

1. **被跳过的邮件**：在邮件抽屉中展示具体跳过原因。规则模式展示命中词（如"命中广告过滤词'促销'"），LLM 模式展示模型的 reason 字段。
2. **低置信度任务**（confidence < 0.7）：任务卡片上展示 LLM 的判断依据。

高置信度任务不需要解释——有价值的信息才值得占用屏幕空间。

## 需求三：规则模式不输出置信度

规则引擎是二值判断——要么命中要么没命中，不存在"75% 确定"。当前 `confidence: 0.0` 硬编码是无意义的占位符。

- 规则命中 → 前端不显示置信度标签
- LLM 补充/判断 → 前端显示 LLM 的置信度
- 实现方式：前端判断 `confidence_source !== 'rules'` 时才展示

## 需求四：宁可误报，不可漏报

两个错误的代价不对称：

- 多一张误生成的任务卡片 → 用户花 2 秒删掉
- 漏一个真任务 → 用户可能错过考试、漏掉客户、耽误审批

**改为**：仅强非任务词触发跳过。弱非任务词（系统通知/登录提醒/账单已生成）不再拦截，交给后续判断。

核心理念：只有**显然不是任务**的才拒绝。存疑的，一律倾向于创建任务。

## 需求五：任务卡片增加发件人

发件人是邮件自带的现成字段，不需要额外提取逻辑。看板上一眼判断邮件来源（"老板发的还是系统发的"），快速筛查。

展示方式：任务卡片分类下方，一行灰色小字。

> 地点暂不独立提取——格式过于多样（A213、302会议室、腾讯会议），LLM 润色 task_name 时附带进去即可，如"参加习概论考试（A213，6/6 10:45）"。
